# DSMC v2.8.7 变更说明

> 起因：页脚版权信息上方要能挂一排友情链接，后台设置后在那里显示。
>
> 这一版只加了一个字段（`friends`）和一块渲染，没动已有数据结构 —— 米表配置
> 读出来仍然向后兼容，老配置里没有 `friends` 就当空数组。

## 一、落点：页脚信息**上方**，且在 `<footer>` **内部**

```
────────────────────────────────────────────  ← .site-foot 的 border-top
友情链接   NieGe 导航  域名论坛  主机测评  免费域名   DSMC 仓库
────────────────────────────────────────────  ← .site-friends 的 border-bottom
[盾] DSMC v2.8.7 · © 2026 Copyright by NieGe Meta · Powered by DSMC · MIT License
域名状态管理器
```

**为什么必须放进 `<footer>` 里**：第一版是把 `<nav class="site-friends">` 拼在
`<footer>` 前面。这样 `.site-foot` 自带的 `border-top` 还在，`.site-friends` 自己
也画了一条上边线，两条线紧挨着出现，看起来像两个互不相干的区块。

现在整块只有一条上边线（页脚起点），友链下方一条细分隔线把它和版权信息分开。

**为什么不塞进 `.sf-line`**：那一行已经是「品牌 · 版权 · Powered by · License」
四段，再塞 5–8 条友链，窄屏会折成三行，四段信息全被冲散。独立一排、`flex-wrap`
折行，折几行都只影响它自己。

## 二、字段：`friends` 与 `nav` 同构但独立

```js
// config:market
nav:     [{ label, url }]   // 顶栏那一排（站内导航语义）
friends: [{ label, url }]   // 页脚那一排（友链语义）
```

**为什么不复用 `nav`**：两者数据结构一样，但落点不同。共用一个字段的后果是
「加一条友链，顶栏也跟着多一项」—— 用户不会想到这两处是联动的。

归一化时两个字段各自走 `normalizeLink()`：

```js
function normalizeLink(raw, labelMax) { … }      // 共用同一套 URL 白名单
normalizeNavItem(raw)    → normalizeLink(raw, 12) // 导航：标签要短
normalizeFriendItem(raw) → normalizeLink(raw, 20) // 友链：站点名通常更长
```

**名称上限不同**：导航项要挤在顶栏一行里，12 字；友链是独立一排，20 字。
一刀切 12 会把「主机测评博客」截成「主机测评博客」…… 更常见的是把
「NieGe 的导航站」截成半截词。

## 三、安全：`href` 的白名单拦两次

友链和导航一样，最终会原样进 `<a href="…">`：

| 输入 | 结果 | 原因 |
| --- | --- | --- |
| `https://dn.example.com` | 保留 | 正常外链 |
| `/market` | 保留 | 站内路径 |
| `javascript:alert(1)` | 丢弃 | 现成的 XSS |
| `data:text/html,<script>…` | 丢弃 | 现成的 XSS |
| `//evil.example.com` | 丢弃 | 看着像站内路径，其实跳别人的域名 |

存储层（`market-store.js`）拦一次，渲染层（`footer.js` 的 `safeHref`）再拦一次。

**为什么渲染层也要拦**：`footerHtml()` 不只被 handlers 调用，预览脚本和单测都
直接调它。只依赖存储层，等于假设「所有调用方都先归一化过」—— 这个假设在
`marketHtml()` 被测试直接调用时就已经不成立了。

`security-audit.mjs` 里补了一项「米表友情链接的伪协议被丢弃」，四项输入里只
留下合法的那一条。

## 四、后台：与「自定义导航」同构的编辑区

米表设置页多了一块：

```
友情链接
┌──────────────┬──────────────────────────────┬───┐
│ 名称（如 域名导航）│ https://… 或 /路径            │ × │
└──────────────┴──────────────────────────────┴───┘
+ 添加友情链接        显示在页脚信息上方，最多 8 项
```

**行属性用 `data-friend-row` 而不是复用 `data-nav-row`**：`saveMarket()` 是按
`[data-nav-row]` 收集顶栏导航的。共用属性会让保存时把友链一并写进 `nav`，
表现是「加一条友链，顶栏多一项」，而且删掉友链那行后顶栏项也跟着没了。

`client.js` 里两边的「添加」按钮合并成一个 `addLinkRow(listId, tplId, kind, label)`，
`kind` 决定查哪些行、给哪个容器插入。删除按钮则统一按
`[data-nav-row],[data-friend-row]` 找最近的一行。

**半填的行照旧忽略**：只填了名称或只填了链接的行，保存时直接跳过，不报错。
用户加了一半又放弃是很常见的事，把它当错误弹出来只会吵。

## 五、验证

- 单测：存储层 8 项（独立字段 / 伪协议 / 长度上限 / 条数上限 / KV 往返）、
  页脚 5 项（空值不渲染 / 位置在 `<footer>` 内且在版权上方 / 渲染层二次拦截 /
  `rel="noopener"` / 引号转义）、后台表单 5 项（回填 / 模板行 / `data-max` /
  两个字段不串味 / 引号转义）、公开页 4 项
- 安全审计：38 项全过（新增「米表友情链接的伪协议被丢弃」）
- 视觉：页脚单独渲染，深色 / 浅色各一张，另加 390px iframe 一张
  —— 5 条友链在 390px 下刚好排满一行，第 6 条折到第二行

**踩到的坑**：`test('公开页没有友情链接时不渲染空容器')` 第一版写的是
`!html.includes('site-friends')`，一直失败 —— 因为 `.site-friends{…}` 这段 CSS
就在同一个响应里。断言必须带元素形态 `class="site-friends"`，否则反过来写
「不该出现」时永远假通过。
